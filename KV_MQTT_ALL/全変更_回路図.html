②-4 影響範囲の調査結果（ハードコード参照ゼロ）

結論：マスタ値を書き換えても他の回路には一切影響しない。
  • マスタ値は FUN BCD_TO_UINT DM20002:Z7 DM1000:Z2 のような形で publish 電文の DeviceId に載せるためだけに使われている（Main のステータス送信処理）。
  • 比較定数などのハードコード参照は全モジュールで 0 件。 旧ID 180種を 16進表記（H7121／$7121）・10進定数（#28961 相当）の 3形式で全数検索して確認済み。
  • 受信側 Main2 は機種名 'S'（シャトル）／'SV'（サーバ）のみを処理対象にしており、 今回変更した 3/6/7/8/9 系の DeviceId は受信経路に登場しない。Main2 側の対応は不要。
外部影響：ACS 側の DeviceId 対応表の更新が必須。 publish される DeviceId が変わるため、上位（ACS）の対応表を必ず同時に更新すること。 特に 新種別 "3" の追加（旧 9x91 → 新 3x01）は、種別そのものが増えるので見落としやすい。

②-5 反映方法（スクリプトボックスはラダーではなくテキスト）

重要： 機器マスタはスクリプトボックス（BOX_ST）の中身＝テキストであり、ラダー回路ではない。 ニモニック（.mnm）取り込みでスクリプトボックスの中身が復元される場合はそれでよいが、 復元されない・空になる場合は、下記のとおりテキストを貼り替える。
  1. KV_MQTT_ALL/スクリプトボックス貼付用.txt を開く。
  2. ファイル内には36ボックス分が並んでおり、うち ★印の18ブロックが今回の変更対象。
    • ★変更あり：STｽﾃｰﾀｽ レーン1〜9（9ブロック）
    • ★変更あり：コンベヤ到着/離席ステーションNO./レーン1〜9（9ブロック）
    • （変更なし）：ｼｬﾄﾙ/ レーン1〜9、ｻｰﾊﾞｰ/ レーン1〜9（計18ブロック・貼り替え不要）
  3. KV-STUDIO で該当スクリプトボックスを開き、中身を全選択して対応ブロックのテキストに差し替える。
  4. 18ブロックすべてについて繰り返す。
  5. 変換（F4）でエラー0件を確認する。
反映には PLC の再起動が必要。 このマスタは LD _FirstScanOn（運転開始時の1スキャンのみON）で 初期化されるため、転送しただけでは値が入れ替わらない。 PLC を再起動する（または PROGRAM → RUN に切り替える）ことで初回スキャンを走らせること。

③ 変更2：シャトル書込フラグON ＋ マルチ化対応フラグ（Main2・4行追加）

③-1 発覚した不具合

(a) シャトルの書込フラグが未実装だった。
三菱PLCへ渡す指示エリアには、指示データが揃ったことを知らせる書込フラグが各ブロックに1ワード用意されている。 サーバ側は @MOV #1 ZF9:Z7 で書込フラグONがすでに実装済みだったが、 シャトル側は指示データ（作業種別・作業No.・列連段など）は書いているのに、 書込フラグ（ブロック+19）をどこにも書いていなかった。

(b) マルチ化対応フラグが ZF へ一切書かれていなかった。
JSON の MultiFlag は抽出処理で DM768 / DM798 / DM828 に格納され、 キュー（DM30028 / DM30058 / DM30088）まで正しく届いていたが、 そこから指示エリア（ZF）へ転記する処理が存在しなかったため、三菱側には永久に渡っていなかった。

③-6 ポイント解説

ZF19:Z7 ／ ZF18:Z7 が D0419／D0418 等になる理由： この時点で Z7 は、直前の「ｼｬﾄﾙNo.1〜No.8… オフセット計算ラング」 （CAL* DM25002 #20 DM25008 → … → MOV DM25014 Z7）によって、 対象号機ブロックの先頭アドレスを指している。 したがって ZF19:Z7 ＝ ブロック先頭 +19、ZF18:Z7 ＝ ブロック先頭 +18 になる （101号機なら D0419／D0418、102号機なら D0439／D0438…）。 既存の MOV DM25101 ZF1:Z7（＋1＝作業種別）と同じ土台なので、号機ごとの計算は不要。
DM30028 がマルチ化対応フラグである根拠： 受信レコードは DM740 を基準に組み立てられており、 +26 ＝ Station（列/ST:Toロケーション）＝ DM766、 +28 ＝ MultiFlag ＝ DM768（JSON抽出処理で MOV #1 DM768 / MOV #0 DM768 と書かれている）。 これがキュー領域へ転送されると DM30000 基準の同じオフセットになり、 DM30026 が Station、DM30028 が MultiFlag となる。 実際 DM30026 は既存回路で MOV.D DM30026 Station／MOV DM30026 Station_SV として Station に使われているため、DM30028＝MultiFlag のオフセット対応は裏付けが取れている。
MultiFlag の格納先が1つしかない件（ユーザー決定事項）： 仕様書上 MultiFlag は Job ごと（1＝マルチ化対応／0＝非対応）に定義されているが、 指示エリア側の格納先はブロックに1ワードしかない（+18）。 そのため Job1 の値（DM30028）を採用する。 Job2（DM30058）／Job3（DM30088）は転記しない。
ON側だけ @MOV（微分実行）にしている理由： サーバ側の既存 @MOV #1 ZF9:Z7 と揃えている。 条件成立の立上り1スキャンだけ書くので、フラグを常時 1 で塗り続けない。 これにより、次章の「受入可OFFで0に落とす」ループが0を書き勝てる（毎スキャン0が優先される）。 なおマルチ化対応フラグはデータであってフラグ制御の対象外なので、通常の MOV（毎スキャン）でよい。

④ 変更3：指示受入可OFF中は書込フラグを0に保つ（Main2・28行追加）

④-1 目的と確定仕様

問題： 相手が「指示受入可」でなくなった（bit4＝OFF）ときに書込フラグを落とす処理が無いため、 受け側が受け付けられない状態でもフラグが立ちっぱなしになる。
確定仕様：
  1. 対象はシャトル・サーバの両方。
  2. 書込フラグだけを 0 にする。指示データ（ZF1〜ZF13 等）はそのまま残す。
  3. 受入可OFFの間はずっと 0（毎スキャン監視）。OFF中に新しい指示が来てもフラグは立たない＝事実上の受付拒否。

計2台。ステータスは1ワード刻み、指示エリアは10ワード刻み。
サーバ側の号機対応が合っている根拠： 既に 4101＝入庫（ZF720 ブロック）／4102＝出庫（ZF730 ブロック）の入替が入っており、 サーバNo.1（ZF190）↔ 4101 ↔ ZF729、 サーバNo.2（ZF191）↔ 4102 ↔ ZF739 で整合する。 このループの +10 刻みはその並びをそのままなぞっている。

④-8 ポイント解説

命令意味・ねらい
MOV DM110 Z1
MOV DM110 Z2		 2本のインデックスを同じ起点（レーン用アドレス）から始める。以降 Z1 はステータス側、Z2 は指示エリア側として別々の刻みで進む。
MOV ZF150:Z1 MR31500 ステータスワードを MR チャネルへ展開して、ビット単位で触れるようにする既存の定石。 送信側 Main の MOV ZF150:Z1 MR30100（r1199）とまったく同じ手法。展開後は MR31504 が bit4＝指示受入可。
LDB MR31504 B接点（ノーマルクローズ）なので、受入可が OFF のときに成立する。 成立している間は毎スキャン下の MOV #0 が走るため、OFF中はずっと 0 に保たれる。
MOV #0 ZF419:Z2 書込フラグ1ワードだけを 0 にする。ZF1〜ZF13 や ZF18（マルチ化対応フラグ）には一切触らない。
CAL+ Z1 #1 Z1
CAL+ Z2 #20 Z2		 ループ末尾でインデックスを次の号機へ進める。ステータスは +1、指示エリアは +20（サーバは +10）。
「事実上の受付拒否」になる仕組み： 変更2のON側は @MOV（立上り1スキャンのみ）、変更3のOFF側は毎スキャン実行。 受入可OFF中に新しい作業指示が来ると、指示データは ZF1〜ZF13 等に更新されるが、 書込フラグは同じスキャン内・以降のスキャンで 0 に上書きされ続けるため立たない。 受け側から見ると「データはあるが書込フラグが立っていない＝取り込まない」となり、拒否として振る舞う。

⑥ KV-STUDIO への取り込み手順

Main も Main2 も FB を含むモジュール（Main は FBCALL 4件）のため、 そのまま .mnm を取り込むとローカル変数（FB内部変数）が失われる。 必ず「書き出し → 削除 → 取り込み → 移植」の順で行うこと。
  1. プロジェクトをフォルダごとバックアップする。
  2. Main2 を差し替える（FB入り）
    1. Main2 のローカル変数を書き出す（変数一覧 → エクスポート）。
    2. プロジェクトから Main2 モジュールを削除する。
    3. KV_MQTT_ALL/Main2.mnm を取り込む（ニモニック読み込み）。
    4. 手順 a で書き出したローカル変数を移植（インポート）する。
  3. Main を差し替える（FB入り・FBCALL 4件）
    1. Main のローカル変数を書き出す。
    2. プロジェクトから Main モジュールを削除する。
    3. KV_MQTT_ALL/Main.mnm を取り込む。
    4. ローカル変数を移植する。
    5. スクリプトボックス（BOX_ST）の中身を確認する。 復元されていれば何もしない。空になっている／旧値のままの場合は、 KV_MQTT_ALL/スクリプトボックス貼付用.txt の ★印18ブロックを 各ボックスへ貼り替える（②-5 参照）。
  4. 変換（F4）でエラー0件を確認する。
  5. PLC を再起動する（または PROGRAM → RUN に切り替える）。
    機器マスタは LD _FirstScanOn で初期化されるため、初回スキャンを走らせないと新採番が反映されない。 この手順を飛ばすと、転送してもDeviceIdは旧値のまま publish され続ける。
  6. PLCへ転送し、⑦のテスト手順を実施する。
手作業で入れる場合（Main2 のみ）： モジュールを差し替えないので、ローカル変数の移植は不要。 ③-5／④-6 のニモニックを該当位置にそのまま入力すればよい。 その際 MR31504／MR31604 は必ず B接点（ノーマルクローズ）、 インデックス付きデバイスは ZF150:Z1 のように「デバイス:インデックス」で入力する。

⑦ テスト手順

#操作期待結果
1 マスタ確認：PLC再起動後、モニタで機器マスタの値を確認する（レーン1）。 DM1000＝$7101、DM1023＝$8108、 DM1064＝$6101、DM1068＝$9101、 DM1070＝$3101、DM1190＝$6101
2 電文確認：MQTT を購読し、ステータス電文の DeviceId を確認する。 新採番で出ること（7101〜7108 / 8101〜8108 / 6101 / 9101 / 3101 …）。 旧値（7121 等）が出ないこと。
3 受入可ONの状態（D0150 の bit4＝1）でシャトル作業指示を送信する。 ZF418（D0418）＝ 電文の MultiFlag 値、ZF419（D0419）＝ 1。 指示データ ZF401〜ZF413 も従来どおり入る。
4 D0150 の bit4 を 0 にする（三菱PLC未接続ならモニタで ZF150 に 0 を書く）。 ZF419 が 0 に落ちる。ZF401〜ZF418 は残っている（消えないこと）。
5 受入可OFFのまま、新しい作業指示を送信する。 ZF419 は 0 のまま（受付拒否）。指示データは更新される。
6 サーバ側も同様に確認する（D0190／D0191 の bit4 と ZF729／ZF739）。 3〜5と同じ挙動。ただしマルチ化対応フラグはサーバに無いので ZF728 は確認対象外。
7 号機違いで確認する（例：ZF151 の bit4 を 0 → ZF439）。 その1台分だけが 0 に落ち、他号機の書込フラグは影響を受けないこと。

補足：手順4のあと受入可を 1 に戻しても ZF419 は 0 のままで、 次の指示受信ではじめてONになる（自動で立ち上がらない）。これは @MOV（微分実行）による意図した挙動。

⑧ 注意事項

  • 本統合版のベースは KV_MQTT_FIX7_FIN2（2026-08-06 08:43 エクスポート）。
  • もし実機に既に FIX8 / FIX9 / FIX10 のいずれかを取り込み済みでも、そのまま KV_MQTT_ALL で上書き取り込みして差し支えない （内容は同一の最終形。FIX10 とは全ファイルがバイト単位で同一）。
  • ACS 側の DeviceId 対応表の更新が必須。 特に新種別 "3" の追加（旧 9x91 → 新 3x01）を忘れないこと。
  • PLC 再起動（または PROGRAM→RUN）を必ず行う。 機器マスタは初回スキャンでしか書かれない。
  • Main／Main2 はどちらも FB入りモジュール。.mnm 差し替え時は ローカル変数の書き出し／移植を忘れない。
  • MR31504／MR31604 は B接点。a接点で入力すると「受入可のときに0を書く」という真逆の動作になる。
  • 変更2の @MOV #1 ZF19:Z7 の @（微分）を落とさないこと。通常 MOV にすると毎スキャン1を書き続け、 変更3の0書きと競合してフラグが落ちなくなる。
  • ループ先頭の MOV DM110 Z1／MOV DM110 Z2 を省略しないこと。 インデックスの再初期化がないと、他処理が残した値を引き継いでまったく別のアドレスを0で潰す危険がある。
  • 変更1は値の置換のみ。スクリプトボックスの行を増やしたり減らしたりしない。
rung_check の警告について： 検証ツール rung_check で MQTTSC_MANAGE_SAMPLE と FB系モジュールに 「終端でブロック残存」という警告が出るが、これらはベースと完全同一の未変更ファイルであり、 FB／サブルーチン構造に対するツール側の制約によるもの。今回の変更とは無関係で、実害はない。
