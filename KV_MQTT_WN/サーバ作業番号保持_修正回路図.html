Main 修正回路図：サーバ作業番号 保持化 不具合修正

サーバの動作完了電文で作業No.が「0」になる不具合を修正する。原因は 完了電文の送信直後に保持していた作業番号をクリアしていたこと（FMOV #0 DM25120 #2 / FMOV #0 DM25125 #2）。赤＝削除、 黄＝命令変更（MRD→MPP）。 対象: Main（サーバ動作完了送信ループ／FOR #2 の中）

① 不具合の原因

症状： サーバの動作完了電文で、作業No.が 0 になることがある。
原因： 荷取と荷置をまとめた1件の作業指示では、三菱側から完了が2回上がる（号機ごとの読込フラグイベント単位）。 ところが完了電文を送信した直後に FMOV #0 DM25120 #2（4102側）／FMOV #0 DM25125 #2（4101側）で 保持していた作業番号をその場でクリアしていたため、1回目の送信でクリアされてしまい、2回目の完了電文では作業No.=0 になっていた。
修正方針（確定）： 送信後のクリアをやめ、次の作業指示（Work_Request）を受信するまで保持する。 次の Work_Request 受信時に Main2 が DM25120/DM25121（4102）・DM25125/DM25126（4101）を 上書きするので、明示的なクリアは不要。
ユーザー確認済み：「作業指示を受けていないのにサーバの動作完了が上がることはない（必ず指示に対応）」→ 古い番号を誤って返す事故は起きない。

② なぜ単純削除ではなく分岐の組み替えが必要か

FMOV #0 DM25120 #2 は独立した1行ではなく、MPS/MPP分岐の最終出力になっていた。 分岐の途中の1本を削除する場合は問題ないが、最終分岐（MPPで始まる枝）を削除するには、 1つ手前の分岐（MRDで始まっていた枝）をMPPに変更して「新しい最終分岐」に昇格させる必要がある。 そうしないとMPS/MPPの段数（スタック深さ）が崩れ、KV-STUDIOがニモニックを読めなくなる。

変更前後とも、この内側分岐は MPS 1回・MPP 1回で対応が取れている（段数は変わらない）。 変わるのは中間分岐の個数（MRD 2回 → 1回）と、最終分岐の中身（旧: 3本目=MRD開始・4本目=MPP開始のFMOV → 新: 3本目がMPP開始の最終分岐になり、4本目は消滅）。

⑤ 反映手順

手作業で直す場合（最も簡単）

KV-STUDIO 上で、Main のサーバ完了ループ（StringMove 'SV' DM21000:Z7 がある FOR #2 の中）で、 FMOV #0 DM25120 #2 と FMOV #0 DM25125 #2 の2つのボックスを削除するだけでよい。 KV-STUDIO上でボックスを消せば、分岐（MPS/MRD/MPP）は自動的に詰まるため、MRD→MPPの付け替えを手で意識する必要はない。

ニモニック取り込みで一括反映する場合

Main は FB入り（FBCSL 4件）のため、ニモニック単体では往復できない。以下の手順を厳守する。

  1. プロジェクトをバックアップする。
  2. 対象モジュール Main のニモニックを書き出す。FB入りのためローカル変数も一緒に書き出す。
  3. モジュール削除 →本修正版 Main.mnm を取り込む。
  4. ローカル変数を移植する（FBインスタンス設定を含む。これをしないと ??? 引数が解決されずエラーになる）。
  5. F4（変換）でエラー0件を確認する。
  6. 動作確認後、転送する。
検証済み： 実機エクスポート KV_MQTT_FLG_FIX の Main をベースに生成。削除6行・追加2行 （実質：MRD→MPP を2箇所、MPP+FMOV を2組削除）。rung_check 合格で MPS/MRD/MPPの段数が釣り合い、終端も正常。decode→encode 往復 IDENTICAL。他6モジュールは無変更。 成果物：/home/ilm/ダウンロード/KV_MQTT_WN/
